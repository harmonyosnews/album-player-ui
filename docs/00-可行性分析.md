## 1. 结论摘要

**可以做，而且不需要改动 aplayer 的音频引擎。**

核心依据：

1. aplayer 2.19 在 `7778` 端口提供了一套完整的同源 JSON HTTP 控制接口，覆盖专辑浏览、曲目播放、暂停/继续、上一首/下一首、进度、音量、网络电台、播放列表、配置读写等核心操作 [E2][E4]。
2. aplayer 自带的 Web 界面本质上是 `/opt/aplayer` 下的静态文件（`aplayer.html`、`aplayer.js`、`aplayer.css`），由 aplayer 进程直接提供。新增子目录下的 `.html/.js/.css/.json` 资源可被正常访问，路径穿越被拒绝 [E5]。因此可以用新前端**原位替换**旧界面，无需新增端口、反向代理或系统服务。
3. `/opt/tinylms` 1.3.4 是一套成熟的 SPA 界面：左侧导航 + 顶部搜索 + 内容区 + 底部播放条 + 全屏正在播放 + 响应式移动端；设计令牌、组件划分、状态推送方式都可以借鉴 [E9]。
4. 目标平台同时存在 ARM64（`.230`）和 x86_64（`.137`）的 aplayer 2.19；静态前端与 CPU 架构无关，一份构建产物可同时覆盖两台机器 [E2][E8]。

**但必须带条件推进：**

| 条件 | 说明 | 处置 |
|---|---|---|
| `.133` 分析时没有 `/opt/aplayer`（Phase 0 已修复） | 只有残留的 `aplayer.service`，目录缺失，服务 inactive [E7] | Phase 0 从 `.137` 复制 x86_64 2.19 并安装 APUI；仅用于开发/构建验证 |
| `.133` 是虚拟机，只有虚拟声卡 | VMware Ensoniq AudioPCI（`snd_ens1371`，仅基础 PCM），不满足真机/DSD 条件；PCM 打开失败时 aplayer 会记录 `unable to open pcm device` 并退出 [E11] | `.133` 只做构建/UI 联调/基础冒烟；真实播放/DSD/声卡测试放 `.137` |
| aplayer 接口无官方文档、无鉴权、无 CORS | `OPTIONS` 返回 501，响应无 `Access-Control-Allow-Origin` [E4] | UI 必须与 aplayer 同源部署；只在可信 LAN 使用；二期可加伴生适配服务做鉴权/SSE |
| `SetConfig` 是“整包覆盖”语义 | 只提交 `covers` 字段会把其余配置重置为默认值（实测 668→900 字节）[E6] | UI 必须先 `GetConfig`，合并完整可写字段后再 POST；安装/升级前备份 `config.dat` |
| aplayer 会话可能回写 `config.dat` | 实测一次包含启动/查询/停止/音量的会话后，配置从 668 B 变为 900 B；触发点未完全隔离 [E6] | 所有测试/部署脚本先备份；不要频繁重启；配置文件纳入版本化备份 |
| 静态资源扩展名白名单 | `.js/.css/.json/.html/.png` 可访问；`.svg/.woff/.woff2/.ttf/.webp/.mjs/.map/.txt` 返回 404 [E5] | 前端构建禁止产出这些文件；图标用内联 SVG data URI，字体用系统字体，图片用 PNG 或 API 返回的封面 |
| 原生接口会暴露文件系统 | `?GetPlaylists&ind=-1` 返回根目录列表 [E4] | 新 UI 默认只展示配置的音乐根目录；文件浏览标记为“高级”，并提示风险 |
| 厂商升级会覆盖 UI | 新版 aplayer 包会替换 `aplayer.html/js/css` | 安装脚本保留备份；升级后重新应用 UI；版本锁定与回归清单 |

**建议决策：GO。** 先按“原位静态 UI 替换”交付 MVP（预计 7–8 周），把“伴生 Go 适配服务 + SSE + 鉴权”作为二期可选项。这样可以在最短路径上获得一个可用的新界面，同时不引入新的系统服务、端口和 init 适配问题。

## 2. 背景与目标

### 2.1 背景

现有 aplayer 的 Web 界面是厂商随播放器发布的传统页面：以表格、图片按钮和 Zepto/jQuery 风格脚本为主，信息密度高、视觉风格陈旧、移动端体验一般。`/opt/tinylms` 的界面则是现代 SPA：深色主题、暖金色强调色、卡片式专辑、底部常驻播放条、全屏正在播放、响应式布局，整体更符合当前音频类产品的使用习惯。

需求是：**在不改变 aplayer 音频路径的前提下，为 aplayer 制作一套新的 Web 操作界面，视觉与交互借鉴 tinylms。**

### 2.2 目标

1. 用新 UI 完整覆盖 aplayer 的核心操作：浏览专辑/艺术家、播放专辑、暂停/继续、上一首/下一首、停止、进度、音量、网络电台、播放列表、输出声卡与常用设置。
2. 视觉与交互达到 tinylms 1.3.4 的水准：深色主题、卡片布局、底部播放条、全屏正在播放、移动端适配。
3. 部署简单：不新增系统服务、不新增端口、不修改 aplayer 二进制和音频配置；一份静态产物同时支持 ARM64/x86_64。
4. 安全可控：所有来自 aplayer 的字符串按不可信内容处理；配置写入可回滚；不扩大现有攻击面。
5. 可维护：源码、构建、部署、回滚、接口契约都有文档和检查脚本。

### 2.3 非目标

以下内容**不在本期范围**，除非另行立项：

- 替换或修改 aplayer 音频引擎、ALSA/Diretta 输出链路、DSD/DoP 处理。
- 播放队列编辑/重排、歌词、标签编辑、智能推荐、听歌历史、多房间/多设备聚合。
- 修改 `7779` 端口的 UPnP 渲染器界面（`ap2renderer`），本期只做播放器 `7778`。
- 将 aplayer 改造成服务端 API 网关；二期可选“伴生适配服务”，但不是 MVP 的前置条件。
- 在 `.133` 虚拟机上做真实听感/DSD/声卡验收。

### 3.1 三台机器的角色与版本

| 机器 | 角色 | 系统 | 架构 | aplayer | tinylms | 关键事实 |

### 3.2 `.230` 上的 aplayer 部署

`/opt/aplayer` 顶层文件 [E2]：

```

aplayer.html            30,082 B   厂商 Web 界面
aplayer.js              51,293 B   Zepto + 原生 JS
```

二进制特征 [E3]：

- `ELF 64-bit LSB pie executable, ARM aarch64, dynamically linked, stripped`。
- 依赖 `libasound.so.2`、`libpthread`、`libdl`、`libm`、`libc`；没有独立的 Web 框架运行时。
- 字符串中可见 `Album Player for Linux 2.19`、`libevent` 的 `evhttp_*`、`json::Reader`、`/home/igor/gitprojects/aplayer-ffmpeg2/...`。
- 说明：aplayer 是一个自带 HTTP 服务的单体程序，UI 资源由它从当前工作目录提供。

服务状态 [E2]：

- `/etc/systemd/system/aplayer.service`：`Type=forking`、`WorkingDirectory=/opt/aplayer`、`ExecStart=/opt/aplayer/aplayer`。
- 当前 `aplayer.service` 为 `inactive (dead)`、`disabled`。
- 端口 7778/7779 空闲。
- 这也解释了为什么分析期间需要临时启动 aplayer；实测会话后 `config.dat`/`aplayer.log` 会变化（具体触发点未完全隔离），必须备份/恢复。

### 3.3 `.133` 上的现状与差异（分析时）

> Phase 0 已执行：`.133` 已安装 x86_64 aplayer 2.19 与 APUI；以下为分析时状态，实施结果见 [06-实施与验收记录.md](06-实施与验收记录.md)。

实测结果 [E7]：

- `/opt/aplayer`：**不存在**。
- `/etc/systemd/system/aplayer.service`：存在，`disabled`，`inactive (dead)`，`ExecStart=/opt/aplayer/aplayer`，因此一旦启用必然启动失败。
- `/opt` 下没有 aplayer 二进制；全盘 `find` 只找到 `/srv/py/logo/aplayer.png`、该服务单元和无关的 Cargo 源码。
- `/opt/tinylms`：1.3.4，但版本文件写的是 `aarch64`，目录里同时有 x64 v2/v3/v4/zen4 与 ARM 静态包，符号链接指向 `tinylms-x64-v2-static_20260620_215612`；服务 disabled/inactive。属于打包/版本标记不一致，不影响本次 UI 方案，但说明 `.133` 的软件包管理需要谨慎。
- 工具链：无 `go`；`node` 不在 PATH，但 `/opt/node22/bin/node`（v22.23.2）和 `/opt/node24/bin/node`（v24.18.0）可用，`pnpm` 可用；gcc 14.2、Rust 1.98、Docker 29.9。
- 根分区 6.3 GB 可用；内存 3.8 GB。
- 虚拟声卡：`/proc/asound/cards` 显示 `Ensoniq AudioPCI`（`snd_ens1371`），只有基础 PCM；不能作为真实听感/DSD/发布前真机验收环境。

**处置建议（Phase 0 已执行）：**

1. 把 `.137` 的 x86_64 aplayer 2.19（`/opt/aplayer`，二进制 md5 `0bd47d5f1ee9a2d372f16d68199d36dd`）复制到 `.133` 的 `/opt/aplayer`，或从官方 `aplayer64.tar.gz` 安装；前端文件与 `.230` 相同（md5 一致），二进制为 x86_64。
2. 在 `.133` 上只验证“UI 能加载、接口能返回、静态资源能提供、构建能通过”；播放/暂停/DSD/声卡切换等真实音频行为放到 `.137`。
3. 为 `.133` 增加一个 **mock aplayer**（见开发手册），在需要可控状态/避免真实音频依赖时联调 UI 状态机。

### 3.4 `.137` 的参考价值

- aplayer 二进制为 x86_64 2.19，6,332,176 B，md5 `0bd47d5f1ee9a2d372f16d68199d36dd`；前端文件与 `.230` 完全同哈希 [E8]。
- 系统没有 systemd，使用 GentooPlayer 的 `supervise-daemon`/OpenRC 体系；因此**新增一个系统服务需要额外适配**，而“原位静态 UI 替换”不需要。
- 9000 端口被 LMS 占用，7778/7779 未占用；适合作为真实播放、网络电台、声卡选择、配置保存/恢复的验收机。

### 3.5 aplayer 官方信息

官方 Linux 页面与安装指南 [E10]：

- 版本 2.19；支持 x86 32/64、ARM v6/v7/v8、ARM64。
- 播放器 Web 界面端口 **7778**；渲染器（`ap2renderer`）界面端口 **7779**。
- 支持 WAV/FLAC/APE/WavPack/ALAC/AIFF/AAC/OGG/MP3/MP4/DFF/DSF/OPUS/TAK/WMA/SACD ISO/DVD-A；DSD 可 Native/DoP/PCM。
- 支持浏览器远程控制、UPnP/DLNA 渲染、scream 流。
- 官方文档**没有**公开 HTTP API；现有接口是从随包前端和实测响应中还原的，属于“事实契约”，不是“承诺契约”。

## 4. 技术可行性

### 4.1 aplayer 的 HTTP 接口足够支撑新 UI

实测与前端代码交叉验证，核心接口如下 [E4]：

| 能力 | 接口 | 实测/推断 |
|---|---|---|
| 读取完整配置 | `GET /?GetConfig` | 实测 200 JSON，101 个字段 |
| 读取专辑/艺术家/年份/曲目/播放列表 | `GET /?GetAlbums` | 实测 200 JSON；空库时数组为空，`Playlists` 返回根目录列表 |
| 读取某专辑曲目 | `GET /?GetSongs&album=N` | 实测无效专辑返回 `{}`；有效结构由前端解析器确认 |
| 播放专辑/曲目 | `GET /?Play&album=N&song=M` | 实测无效参数返回 `{"Result":"Can't play file"}` |
| 停止 | `GET /?Stop` | 实测 `{"Result":"OK"}` |
| 暂停/继续 | `GET /?Pause` | 前端使用，响应 `{"Result":...}`（推断） |
| 上一首/下一首 | `GET /?Prev`、`/?Next` | 前端使用（推断） |
| 进度跳转 | `GET /?Position&pos=0..100` | 前端传百分比（推断） |
| 音量 | `GET /?SetVolume&volume=0..100` | 实测返回 `{}`；音量禁用时无实际效果 |
| 播放状态 | `GET /?State` | 实测 200 JSON，17 个字段，1 秒轮询 |
| 封面 | `GET /?GetImage&pl=&image=&time=` | 实测 200 PNG；响应有重复 `Content-Type` |
| 网络电台 | `GET /?RadioMode`、`/?GetRadio`、`/?GetPictures`、`/?Favor` | 部分实测/前端确认 |
| 电台增删 | `POST /?AddStation`（JSON）、`GET /?DeleteStation...` | 前端确认 |
| 播放列表 | `GET /?GetPlaylists&ind=N`、`/?GetPlaylist&playlist=N`、`/?SavePlaylist&name=`、`/?DeletePlaylist&name=` | 实测/前端确认 |
| 配置写入 | `POST /SetConfig`（完整 JSON） | 实测，响应文本 `Settings saved!` |
| 选择声卡 | `GET /?SelectCard&card=N` | 前端确认；会停止播放并重新配置 |
| 退出播放器 | `GET /stop` | 实测文本 `Player stopped!` |
| 电台目录更新 | `GET /?Update0`（Update）、`/?Update1`（Replace） | 前端确认；会联网改 `Radio/` |

**结论：** 除“队列编辑、歌词、标签、历史”等 aplayer 本身没有的能力外，tinylms 的核心播放/浏览/电台/列表/设置能力都有对应接口。新 UI 可以做，但必须按 aplayer 的“专辑制”模型设计，而不是照搬 tinylms 的“队列制”模型。

### 4.2 原位静态替换可行

实测 [E5]：

- aplayer 从当前工作目录提供 `/aplayer.html`、`/aplayer.js`、`/aplayer.css`、`/img/logo.png`。
- 新增子目录 `ui/` 下的 `.js`、`.css`、`.json`、`.html` 可正常返回，MIME 分别为 `text/javascript`、`text/css`、`application/json`、`text/html`。
- 深层路径 `ui/assets/deep.js` 可访问。
- `/../etc/passwd` 返回 404，未发现路径穿越。
- `.svg`、`.woff`、`.woff2`、`.ttf`、`.webp`、`.mjs`、`.map`、`.txt` 返回 404。
- 目录索引 `/ui/` 返回 404。

这意味着：

1. 新 UI 可以作为 `aplayer.html` 的替代入口，引用 `ui/app-<hash>.js` 和 `ui/app-<hash>.css`。
2. 不需要 HTTP 反向代理、不需要新端口、不需要改 aplayer 二进制。
3. 前端构建必须遵守白名单：**单文件 JS + 单文件 CSS + 可选 JSON/PNG；禁止 SVG 文件、字体文件、WebP、`.mjs`、sourcemap**。图标用内联 SVG data URI，字体用系统字体，占位图用 PNG 或 CSS 渐变。
4. 由于 aplayer 对 `/` 固定返回 `aplayer.html`，替换入口文件即可生效；实测**运行中替换**后下一次 `GET /` 立即返回新内容，API 不受影响（E13）。建议用原子 rename 避免半写入，不需要重启 aplayer。

### 4.3 同源约束与 CORS

实测 [E4]：

- `OPTIONS /?GetAlbums` 返回 **501 Not Implemented**。
- 响应中没有 `Access-Control-Allow-Origin`。
- 所有 JSON 响应 `Connection: close`，没有 keep-alive。

因此：

- 如果把新 UI 部署在另一个端口/域名，浏览器会因 CORS 预检失败而无法调用 aplayer。
- **原位静态替换是唯一无需额外中间层的同源方案**。
- 如果二期要做独立端口的 UI/鉴权/SSE，必须加一个同源反向代理或伴生服务，由它代理 aplayer；这是二期架构，不是 MVP 必需。

### 4.4 tinylms 界面的可借鉴点

`/opt/tinylms/public` 1.3.4 [E9]：

- `index.html` 826 行，`style.css` 4,901 行，`app.js` 661 行，`app.legacy.js` 171 KB（数千行），`modules/` 下有 `api.js`、`utils.js`、`ui-components.js`、`info-panel.js`、`tag-editor.js`。
- 布局：左侧 260 px 导航、顶部搜索、内容视图、底部 128 px 播放条、全屏正在播放、右侧详情栏、移动端底部导航。
- 主题：默认深色 `#0a0a0a/#141414/#1e1e1e`，强调色暖金 `#d4a574`，文字 `#fff/#b8b8b8`，圆角 4/8/12/16 px，三档阴影，150/250/400 ms 过渡。
- 组件：hero、媒体卡片、横向滚动、专辑网格、艺术家卡片、列表行、标签页、开关、滑块、模态框、Toast、空状态、骨架屏。
- 状态：`/api/status` + `/api/events` SSE，页面隐藏时暂停渲染，5 秒兜底同步。
- API：REST `/api/...`，前端通过 `modules/api.js` 统一封装。

**可借鉴：** 布局、设计令牌、组件形态、响应式断点、播放条/全屏播放、状态轮询/可见性处理。
**不可照搬：** 队列编辑、智能电台、标签编辑、歌词、收藏（歌曲/专辑）、多目标 Diretta、UPnP 设置、媒体库扫描——这些依赖 tinylms 后端，aplayer 没有对应能力。

### 4.5 架构方案比较

| 方案 | 做法 | 优点 | 缺点 | 适用 |
|---|---|---|---|---|
| **A. 原位静态 UI 替换（推荐 MVP）** | 新 SPA 构建为 `aplayer.html + ui/*.js/css`，替换 `/opt/aplayer` 中的旧界面 | 同源、零新服务、零新端口、跨 init 系统、资源占用最低、架构无关 | 无服务端鉴权/SSE/参数校验；厂商升级会覆盖；原生 API 仍暴露 | 可信 LAN、单机播放器、快速交付 |
| **B. 伴生 Go 适配服务 + SPA** | Go 静态二进制监听 7780，代理 7778，提供 SSE/鉴权/校验/配置备份，内嵌 SPA | 解决 CORS/鉴权/SSE/配置安全；aplayer 不受改动；可扩展 | 多一个进程/端口；`.137` 无 systemd，需要 OpenRC/supervise 适配；开发量更大 | 产品化、多人/远程访问、需要审计 |
| **C. 独立前端 + iframe 嵌入旧 UI** | 新壳页面 iframe 旧界面 | 改动最小 | 无法真正控制播放、样式不可控、跨域/点击劫持问题 | 不推荐 |
| **D. 修改 aplayer 二进制/反编译** | 直接改内置 UI/服务 | 理论上最彻底 | 闭源、无源码、破坏签名/升级、风险极高 | 不做 |

**决策：A 作为 MVP；B 作为二期可选。** 理由：

- `.137` 是 GentooPlayer，没有 systemd；B 需要额外 init 适配，A 不需要。
- aplayer 的核心价值是低资源、低干扰；A 不增加常驻进程。
- A 的同源特性直接绕过 CORS 501 的限制。
- A 的配置风险可以用“完整配置合并 + 备份/导出/导入 + 安装脚本备份”控制到可接受。
- 如果后续需要鉴权/SSE/审计，再把同一套 SPA 的 API 基址切到 B 的 `/api`，前端资产可复用。

| 歌词 | 无 | **不做** |
| 标签编辑 | 无 | **不做** |

| 媒体库扫描 | aplayer 自动扫描/根目录配置 | **不做**：只提供根目录设置与状态，不实现扫描器 |

| 全屏正在播放 | 前端能力 | **做** |
| 移动端 | 前端能力 | **做**：底部导航 + 紧凑播放条 |

### 5.2 覆盖度评估

- **播放控制**：100%（播放/停止/暂停/上下曲/进度/音量）。
- **浏览**：90%（专辑/艺术家/曲目/封面；缺服务端搜索、歌词、标签）。
- **电台**：90%（分类/播放/收藏/增删；依赖 `.rad`/`.m3u` 目录结构）。
- **播放列表**：80%（加载/保存/删除；aplayer 的列表语义与 tinylms 不同，需要 UI 解释）。
- **设置**：85%（字段齐全；DSD/DSP/卷积属于高风险高级项，默认折叠）。
- **队列**：只读查看/保存 100%，编辑/重排 0%（aplayer 无接口）。
- **历史/收藏/推荐**：0%（aplayer 无此能力，明确不做）。

**总体：核心听音操作可 100% 覆盖；tinylms 的扩展功能约 60–70% 可覆盖。** 新 UI 的定位应是“更好的 aplayer 遥控器”，不是“复刻 tinylms 的全部功能”。

## 6. 非功能可行性

### 6.1 性能与资源

- 静态前端：构建后预计 JS < 300 KB gzip、CSS < 80 KB gzip；首次加载 2–4 个请求；无框架运行时。
- 轮询：`?State` 每秒 1 次，响应约 328 B；与厂商 UI 相同；页面隐藏时降到 5 秒或暂停。
- 内存：浏览器标签页为主，预计 30–60 MB；不新增系统进程。
- `.230` 根分区仅剩 901 MB：静态产物 < 2 MB，部署无压力；构建在 `.133` 完成。
- aplayer 的 `Connection: close` 意味着每秒新建一次 TCP 连接；LAN 下可接受。若二期需要 SSE/长连接，用伴生服务解决。

### 6.2 兼容性

- 前端：Chrome/Edge/Firefox/Safari 最近两个大版本；iOS Safari 15+；Android Chrome 100+。
- 构建目标：ES2020；不使用可选链之外的过新语法，或由 Vite 转译。
- 架构：静态资源与 CPU 无关；`.230` ARM64、`.137` x86_64 共用一份 `dist`。
- 端口：继续使用 7778，不新增端口；不触碰 7779。
- init：不新增服务，systemd/OpenRC 均无需改动。

### 6.3 安全

现有 aplayer 的安全边界：

- 无鉴权；任何能访问 7778 的人都能控制播放、读配置、浏览文件系统。
- 无 CORS；`OPTIONS` 501。
- `GetPlaylists` 会返回根目录列表；`GetPath` 可返回路径/URL。
- 播放列表名称等字段可能包含 HTML（厂商 UI 直接 `append`），存在 XSS 风险。

新 UI 的改进与边界：

- **必须**把所有 aplayer 字符串当不可信内容：`textContent`、属性白名单、URL 协议白名单；禁止把 `Playlists`/`conv_list` 等 HTML 字符串直接 `innerHTML`。
- 不新增鉴权；**部署范围限可信 LAN**；如需远程访问，二期上伴生服务加 Basic Auth/Token + TLS，或前置反向代理。
- 文件浏览默认只显示配置根目录；不提供“删除文件”能力；删除类操作只限 aplayer 的播放列表/电台条目，并二次确认。
- 配置写入前校验范围；保存前导出 JSON 备份；安装/升级前备份 `config.dat`。
- 不在 UI 中显示 `api_key`/`api_cx` 等敏感字段。

### 6.4 可维护性

- 前端源码 TypeScript + 原生模块，无框架锁定；构建 Vite；测试 Vitest/Playwright。
- API 契约以本文档 + fixtures 固化；aplayer 升级时跑契约测试。
- 静态资源白名单检查纳入 CI：构建后扫描 `dist/`，出现 `.svg/.woff/.ttf/.webp/.mjs/.map/.txt` 直接失败。
- 安装/卸载/回滚脚本化；厂商升级后一键重放 UI。
- 版本号：UI 独立版本（如 `1.0.0`），与 aplayer 2.19 兼容性矩阵记录在 README。

## 11. 术语

| 术语 | 说明 |
|---|---|
| aplayer | Album Player for Linux，闭源免费播放器，自带 7778 Web 服务 |
| tinylms | `/opt/tinylms` 的 LMS 兼容播放器/界面，本项目借鉴其视觉与交互 |
| 原位静态替换 | 用新 `aplayer.html/js/css` 替换 `/opt/aplayer` 中的旧界面，不新增服务 |
| 伴生服务 | 独立进程，代理 aplayer 并提供鉴权/SSE/校验；二期可选 |
| fixtures | 从真实 aplayer 抓取并脱敏的接口响应样本，用于契约测试 |
| 整包覆盖 | `SetConfig` 会用请求体重建配置，未提交字段回到默认值 |
